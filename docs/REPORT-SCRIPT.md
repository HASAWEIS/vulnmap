# vulnmap 汇报稿（评审版，约 12 分钟）

## 开场

各位老师好，我汇报的题目是《vulnmap：面向真实开源项目的漏洞挖掘与验证平台》。

这个工作要解决的问题不是“让模型聊出一个漏洞”，而是三个更工程化的问题：第一，漏洞结论能不能复现；第二，结论能不能证伪；第三，产生结论的责任能不能归属到具体阶段、具体输入和具体工具。围绕这三点，我把系统做成了一条受约束的五阶段流水线，并在验证阶段嵌入了一个有界的模型循环。

先给结论：目前台账有 30 个案例、23 个本地双端通过、9 个高危标记；其中 1 个是模型生成路径，3 个是构造器路径，5 个是规则或手工路径。未知任务盲测 4 个，成功 0 个。所以我的定位是“规则/构造器驱动的复现流水线，加模型辅助循环”，不是已经证明自主泛化能力的挖掘 Agent。

## 一、整体架构：workflow 为骨架，局部嵌 agent loop

第一张图讲的是控制结构。

系统没有采用“多个 Agent 自由协商”的架构，原因是那类系统在工程评审里有两个硬伤：失败不可复现，错误不可归因。同一个任务跑两次，路径不同，你很难判断是模型能力问题、工具问题，还是环境问题。

因此我选择 workflow 作为骨架：Orchestrator 负责阶段路由、预算、检查点和失败降级；Recon 是确定性规则；Locate 是确定性流程加一次模型调用；Verify 是固定循环控制器，内部才允许模型提案；Exploit 按需；Report 是固定门禁。

这里的关键不是“用了模型”，而是把模型限制在可审计的边界内：模型只负责提假设和候选字节，是否执行、执行几次、何时停止、结果是否成立，全部由平台判定。换句话说，这是一个 workflow-driven agent，而不是 autonomous agent。

## 二、工具链：按职责分层，按证据准入

第二张图是运行时工具。我按职责把它分成五组：

感知组用自研的 binscan 做源码函数、行号、magic 和调用者扫描；执行组用 Docker，固定 `--network none` 和非 root 用户；诊断组解析 ASAN/MSAN 报告和退出码；构造组由 builders 和 harness 组成，前者负责格式编码，后者从 fuzzer 源码里抽输入长度窗口和种子；决策组是 DeepSeek 接口；证据组是 SQLite、台账和只读前端。

这里有两个容易被问到的取舍。第一，为什么不用 IDA 或 Ghidra。因为当前 benchmark 是源码加容器内预编译二进制，ASAN 能直接给出 `file:line`，源码检索和符号工具已经够用；反编译工具真正有价值的是无源码固件和 stripped 二进制，那是另一条链路，我没有把它画进已实现能力。第二，为什么不用 AFL。因为任务是“给定崩溃描述，构造能复现的输入”，不是从零 fuzzing；真实 fuzzing 会引入新的不确定性和算力成本，不适合作为课程交付的主路径。

## 三、系统分层：展示、编排、执行、工具、证据分离

第三张图是总体架构。左侧是主程序链路，右侧是五层。

我想强调三个设计不变量。第一，展示层只读。页面不能直接改验收状态，重跑也必须先备份旧产物，再走完整 pipeline。第二，检查点绑定镜像 digest、输入哈希和工件哈希；没有 digest 不允许构造检查点，这是为了防止“环境不明却声称复现成功”。第三，证据与声明分离。数据库里 evidence 和 claim 是两张表，模型说的位置是 claim，只有被执行验证过的才是 evidence。

这三点决定了系统不是“跑完就给结论”，而是“每一步都留下可复核的痕迹”。

## 四、技术路线：五阶段，每阶段有输入、输出和失败语义

第四张图是技术路线。

任务准备阶段固定任务 ID、源码版本、镜像和允许资料清单，并区分开发样本与正式评测集。侦察定位阶段做仓库结构、构建方式、解析入口和攻击面梳理，输出结构化 findings。输入构造阶段是最容易产生“特化”质疑的地方，所以我把规则/构造器基线和模型候选分开记录：模板来源、专用分支、候选哈希都要落盘，`allow_builders=false` 时可以强制关闭构造器，只走模型路径。

运行验证阶段用同一输入跑 vul 和 fix，要求 vul 触发、fix 干净，并且崩溃帧与声明 sink 对齐；环境错误、超时、错根因都判失败，不允许用“程序崩了”代替“漏洞成立”。复核交付阶段做独立性、CWE、严重性六维论证、材料完整性和回执核对；缺证据就输出 draft 和 blockers，不直接标可交付。

这五阶段的核心思想是：构造与验证分离，验证与交付分离。

## 五、单任务流程：三条轨道，三种判据

第五张图是单任务流程。

任务准入之后走同一条主链路，但在验证阶段按 benchmark 分流。CyberGym 的判据是双端对照加根因匹配；ExploitGym 的判据是授权靶机执行 EXP，并且要有官方判定或可重放证据，仅拿到 flag 字符串不足以交付；VulnGym 和自选 OSS 的判据是固定源码与运行条件下的可达性、影响和修复对照，不能拿定位行号代替高危。

失败恢复分三类：环境异常，修复后重跑；未触发或错根因，把诊断反馈给模型，调整假设或输入；预算耗尽，停止并归档失败。三条原则是失败不删除、历史不回填、流程完成不等于验证通过，更不等于高危成立或课程可交付。

## 六、结果与效度分析

当前结果是 30 个案例、23 个本地双端通过、9 个高危标记。9 个高危里，CG-07 是模型路径；CG-14、CG-31、CG-36 是构造器路径；其余是规则或手工路径。模型新增贡献只有 1 个。未知任务盲测做了 4 个，成功 0 个；ExploitGym 有历史记录声称官方 socket 10/10，但当前缺少 controller 和 seed，未复核、未重验，所以官方接受状态记为待核。

这里必须做效度分析。构念效度上，崩溃不等于高危，所以高危要求六维论证和 CVSS；内部效度上，构造器和模板会污染“自主性”，所以我把生成路径拆成 builder/model/none；外部效度上，当前 benchmark 以源码型解析器为主，结论不能直接外推到固件和网络服务；统计效度上，样本只有 30 个，盲测只有 4 个，不能做强结论。

## 七、结论与下一步

总结一句：平台底座已经够用，五阶段、证据链、检查点、双端验证和台账都可追溯；当前瓶颈不是架构复杂度，而是可交付证据和自主性证明。

下一步三件事：第一，把 CG-07 做成完整样板案例，补齐参数、轨迹、日志、哈希和人工复核；第二，收口 ExploitGym，拿到 controller 或 seed 后重放；第三，冻结代码，在未知任务上继续验证模型能力，成功和失败都保留。
