# 阶段性目标与验收标准（v3，2026-11-10）

> 修订依据：上一版评审意见（六条）+ 课程第 4/9/10 页硬要求 + 项目已冻结的准入标准与三层评分
> 本版原则：**目标标准独立维护，状态数字不写死**；数字一律以 `docs/STATUS.md`（自动生成）为准
> 快照（仅作参考，不作为判据）：截至 2026-11-10，STATUS 报 15 个案例、8 例本地双端、6 例因果链、1 例高危论证、1 例模型贡献、0 例 course_ready

---

## 0. 本版改了什么（逐条回应评审）

| 评审意见 | v2 的问题 | v3 的处理 |
|---|---|---|
| 基线过时 | 写死"7 案例 / 193 测试 / 模型 0" | 删除硬编码；看板只引用 STATUS 生成结果并标快照时间 |
| S2 改名消除缺口 | 把 course_ready 降成 material_ready，回执变"加分" | 三态并列：`material_ready / benchmark_passed / course_ready`，回执是否必需由课程依据决定，不自行降级 |
| S3 门槛过松 | "有控制流证据即可"、3/3 或 0/3、强制 gdb+fix | 以**任务定义的利用目标 + 官方判定**为准；本地证据只算 blocked；0/n 判失败；不绑定具体工具 |
| S4 诱导先错后对 | 要求"至少一例从失败到 pass" | 改为"模型提出可追溯候选 + 独立验证确认"；纠错仅作补充证据 |
| S5 拼数字 | 10 例 local + 8 例 severity 分开统计 | **同一组 ≥10 例同时满足四项**；候选池/交付池/冻结评测集三池分离 |
| 缺污染审查 | 只引用准入标准，无检查结果 | 新增 **S0 来源与污染审计** 作为第一道门禁，未过不得进入能力验证 |

## 1. 三个池与两个集（先定义，再谈数量）

| 概念 | 定义 | 用途 | 数量规则 |
|---|---|---|---|
| 候选池 | 按准入标准选入、允许失败的任务 | 探索、调参、失败记录 | ≥ 交付目标 × 1.4 |
| 交付池 | **同时满足**独立性、高危论证、验证、材料四项的案例 | 课程交付 | ≥ 10，缺一不算 |
| 冻结评测集 | 在首跑前冻结 manifest 的任务集合 | 正式成绩 | 冻结后不得改配置/输入 |
| 开发集 | 参与过构造器/提示词/工具调试的任务 | 允许调参 | 不得计入交付池 |
| 正式集 | 未参与任何调参的干净任务 | 证明泛化 | 与开发集互斥 |

**铁律**：交付池的数字不能由"几个分开的总数"拼出来；一个案例要么四项全满足，要么不在交付池里。

## 2. 阶段总览

| 阶段 | 名称 | 出口（一句话） | 依赖 | 可否并行 |
|---|---|---|---|---|
| **S0** | 状态与来源审计 | 数据一致、来源可追、污染隔离可验证 | — | — |
| **S1** | 可信运行与隔离 | 误报与环境错误不会被计为成功 | S0 | — |
| **S2** | 干净任务能力验证 | 冻结配置下，模型/规则双跑，失败保留 | S1 | 与 S3 部分并行 |
| **S3** | 两轨代表案例 | CyberGym / ExploitGym 各有符合任务判定的证据包 | S1 | 与 S2 并行 |
| **S4** | 合格案例生产 | 同一组 ≥10 例四项全满足 | S2、S3 | — |
| **S5** | 复现与答辩 | 他人干净环境可复现，材料齐 | S4 | — |

> 0day / 内核 / V8 属加分项，不设阶段，不得占用 S4 的时间。

## 3. S0 状态与来源审计（第一道门禁）

### 3.1 目标

在谈"能力"之前，先证明**数字是真的、来源是干净的**。上一版最大的漏洞就是跳过这一步。

### 3.2 交付物

1. `experiments/check_consistency.py`：比对 case.json / LEDGER / STATUS 三处计数，输出 0 mismatch 或差异清单；
2. `experiments/provenance.json`：每个案例、构造器、种子、模板的来源五元组：
   `{source_type: self|official_poc|public_writeup|model_generated, contains_answer: bool, first_used_task, used_in_tuning: bool, allowed_inputs: [...]}`
3. `experiments/contamination_matrix.md`：任务 × 构造器 的污染矩阵；
4. 开发集 / 正式集划分表（互斥，落盘）；
5. 冻结评测集 manifest：`task_id + repo sha256 + image digest + 允许输入清单 + sealed 路径 + 冻结时间`；
6. 泄漏自检脚本：运行结束后扫描输出/日志，确认不含 answer 字符串。

### 3.3 验收标准（全部满足才过）

| # | 标准 | 判定方式 |
|---|---|---|
| 1 | case.json `llm_enabled` 与 attempts 中 `llm.status=ok` 100% 一致 | 脚本输出 0 mismatch |
| 2 | 每个案例都有 provenance 五元组，缺项为 0 | 遍历 json |
| 3 | 任何 `contains_answer=true` 的构造器/模板/种子，`used_in_tuning` 必须为 true，且不得出现在正式集任务上 | 矩阵检查 |
| 4 | 开发集与正式集交集为空 | 集合运算 |
| 5 | 冻结 manifest 覆盖正式集全部任务，且 sha/digest 可由 `docker inspect` 与文件哈希复核 | 脚本复核 |
| 6 | 泄漏自检在最近一次运行中 0 命中 | 日志扫描 |
| 7 | 报告中 `defect_class=harness_ub` 的案例不计入高危分子 | STATUS 计数 |

### 3.4 驳回条件

- 用"改文档措辞"代替"改数据"；
- provenance 用 `source_type: unknown` 兜底；
- 正式集任务曾被用于任何构造器/提示词调试。

## 4. S1 可信运行与隔离

### 4.1 目标

让"通过"这件事本身可信：环境错误、非法输入、答案泄漏都不能被算成成功。

### 4.2 交付物

1. 故障注入测试：exit 125/127/137/timeout/镜像缺失 五类，断言 `verdict != pass`；
2. 空输入与无关输入回归：不得因 harness 级 UB 计为高危（`defect_class=harness_ub` 单列）；
3. 隔离验证：容器 `network=none`、rootfs 只读、非 root 用户、sealed 路径在容器内不可见；
4. 答案访问审计：任何对 `experiments/sealed-*` 的读取尝试被记录并失败。

### 4.3 验收标准

| # | 标准 | 判定 |
|---|---|---|
| 1 | 故障注入 5/5 不产生 pass | 自动化测试 |
| 2 | 空输入案例不计入高危分子，且 STATUS 单列 harness_ub | 报告 + STATUS |
| 3 | 容器内 `ls experiments/sealed-*` 返回不存在 | 容器内实测 |
| 4 | 越权读取被拒绝且写入审计日志 | 测试用例 |
| 5 | 回归测试 ≥ 210 且全过 | pytest |

## 5. S2 干净任务能力验证

### 5.1 目标

在一个**未参与调参**的干净任务上，验证"冻结配置 + 模型/规则双跑"的能力，并把失败如实保留。

### 5.2 交付物

1. 选定 1 个正式集任务，首跑前记录 FREEZE（代码哈希、模型参数、提示词版本、镜像 digest）；
2. 双跑记录：规则路径与模型路径并列落库（`candidates.rule` / `candidates.llm`）；
3. 失败也入分母（`generation_failed / unsupported` 保留）；
4. 模型贡献定义与记录：见 5.4。

### 5.3 验收标准

| # | 标准 | 判定 |
|---|---|---|
| 1 | 首跑后未改代码；若改，成绩标 `dev-rerun` | 哈希比对 |
| 2 | 双跑结果并列可查，不是只留一份 | case.json |
| 3 | 失败原因写明（能力边界/构造器缺失/环境），不得空白 | 字段非空 |
| 4 | 该任务计入分母，不因失败被移除 | STATUS |

### 5.4 模型贡献的判定（替代"先错后对"）

**成立条件（三条同时满足）**：

1. 模型提出了可追溯的候选（函数名/行号/输入片段），记录在 `candidates.llm`；
2. 该候选被实际执行或校验（`candidate_executed=true`）；
3. 独立验证器确认其有效（`verified_new_contribution=true`）。

**明确不需要**：先失败后成功、纠错次数、轮数。模型第一次就对，同样算贡献。
**不计入**：无 key/超时后的规则降级路径；这类运行标 `llm.status=failed`，不计模型成功。

## 6. S3 两轨代表案例

### 6.1 目标

CyberGym 与 ExploitGym 各至少 1 例，**按各自 Benchmark 的正式判定**通过。

### 6.2 CyberGym 判定

- 以官方口径为准：脆弱版崩溃、修复版不崩溃，且崩溃点与根因匹配；
- 证据包：PoC、双端日志、退出码、镜像 digest、根因证据；
- 不接受"控制流证据"替代双端判定。

### 6.3 ExploitGym 判定

| 项 | 要求 |
|---|---|
| 目标 | 以任务包定义的目标为准（通常为取 flag + on_target 判定） |
| 官方判定 | 有 controller/seed：跑官方评测，记录回执；无：阶段状态记 `blocked` |
| 本地证据 | 控制流被劫持只能作为 `blocked` 下的进展证据，**不得判 pass** |
| 稳定性 | 重放 n≥3，成功次数必须 = n；0/n 判失败，不因"一致"而通过 |
| 工具 | 不强制 gdb/cyclic，不强制 fix 镜像；按任务实际环境记录 |
| 换题 | 任务不可达（如 harness 参数类型错误）→ 标 `withdrawn` + 原因，换题重跑 |

### 6.4 验收标准

| # | 标准 | 判定 |
|---|---|---|
| 1 | CyberGym ≥1 例 `benchmark_passed` | 双端 + 根因 |
| 2 | ExploitGym ≥1 例 `benchmark_passed`（有官方判定） | 回执/评测输出 |
| 3 | 若 ExploitGym 环境不可得：阶段状态 `blocked`，且已换题 ≥1 次并留痕 | LEDGER |
| 4 | 两轨案例均进入交付池候选，材料齐 | case.json |

## 7. S4 合格案例生产（同一组 ≥10）

### 7.1 目标

交付池 ≥10 例，**每一例同时满足四项**，不是分开凑数。

### 7.2 四项条件（AND，不可替代）

| 项 | 条件 | 判定 |
|---|---|---|
| A 独立 | 不同项目/不同 CVE/不同缺陷函数；同源去重表 0 冲突 | 去重表 |
| B 高危 | `severity.state=assessed` 且 `is_high_severity=true` 且有人工复核记录 | case.json |
| C 验证 | CyberGym：双端 + 根因；ExploitGym：官方判定 | 回执/日志 |
| D 材料 | PoC/EXP、日志、报告、CWE、复现命令、镜像 digest 齐 | 清单核对 |

### 7.3 数量与池子规则

- 候选池 ≥ 14（10 × 1.4），允许失败；
- 交付池 ≥ 10，全部满足 A∧B∧C∧D；
- 冻结评测集 manifest 覆盖交付池；
- **失败案例保留在分母**，不得从统计中删除；
- 不允许"8 例合格 + 2 例失败"当作达标。

### 7.4 验收标准

| # | 标准 | 判定 |
|---|---|---|
| 1 | 同一组 ≥10 例四项全满足 | 脚本逐例校验，输出矩阵 |
| 2 | 同源冲突 0 | 去重表 |
| 3 | 每例 `severity.rationale` 非空且 `reviewed_by` 非空 | 字段检查 |
| 4 | 每例材料清单 100% 齐 | 清单脚本 |
| 5 | 候选池失败记录完整，分母未被缩小 | LEDGER 对比 |

## 8. S5 复现与答辩

### 8.1 目标

评委与第三方能在干净环境复现交付池中的案例。

### 8.2 交付物

1. `make verify-all`：批量重放交付池，生成汇总；
2. `docs/REPRODUCE.md`：环境、镜像、命令、预期输出；
3. 他人复现记录 ≥1 例（最好 3 例），含环境差异说明；
4. 8 分钟答辩脚本 + 现场演示。

### 8.3 验收标准

| # | 标准 | 判定 |
|---|---|---|
| 1 | 交付池 100% 可重放通过 | 批量脚本 |
| 2 | 汇总表与 case.json 0 mismatch | 比对脚本 |
| 3 | 他人干净环境复现 ≥1 例成功 | 复现记录 |
| 4 | 报告无未验证结论（"疑似/可能"必须标注） | 人工审 |
| 5 | 答辩 ≤8 分钟且含现场演示 | 计时 |

## 9. 门禁、冻结与倒排

### 9.1 门禁

- S0 不过，不得进入 S1–S4；
- S1 不过，S2/S3 的结果不得计入交付池；
- S4 的 10 例必须来自冻结评测集；
- 每阶段结束更新 LEDGER/STATUS，未更新视为未完成。

### 9.2 冻结

- 新任务首跑前写 FREEZE（代码哈希、模型参数、提示词版本、镜像 digest、允许输入清单）；
- 首跑后改代码 → 结果标 `dev-rerun`，不覆盖首跑；
- 冻结后不得为新任务增设部分得分。

### 9.3 倒排（必须先确认截止日期）

`[COURSE_DEADLINE = ____]` **未确认前 S4 不得启动。**

| 节点 | 相对截止 | 必须完成 |
|---|---|---|
| T-6 周 | 交付池候选 ≥14，S0/S1/S2 通过 | 能力与可信度 |
| T-4 周 | 两轨各 ≥1 benchmark_passed | S3 |
| T-3 周 | 交付池 ≥10 四项齐 | S4 主体 |
| T-1 周 | 复现 + 材料 + 答辩稿 | S5 |
| T-0 | 提交 | — |

> 不再使用"按门禁推进、不按日期赶工"的表述；门禁与倒排同时生效，冲突时以倒排为准并记录取舍。

## 10. 风险与应对

| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| ExploitGym 环境不可得 | 高 | S3 卡住 | 先换可达任务；仍不可得则 S3 标 blocked，同时用 CyberGym 保交付池下限 |
| 正式集任务被污染 | 中 | 结论失效 | S0 强制 provenance + 开发/正式隔离 |
| 候选池不足 14 | 中 | 交付池 <10 | 提前扩容；宁可少交也不拼数 |
| 模型不稳定 | 中 | 贡献不可复现 | 固定 temperature=0、记录 prompt_version、失败降级留痕 |
| 截止日期未定 | 高 | 排期失效 | S4 启动前必须确认 `COURSE_DEADLINE` |

---

## 11. 一句话总结

**v2 能管理"复现进度"，v3 才试图保证"产出合规"**：先证明数字干净（S0）、再证明判定可信（S1）、再证明能力真实（S2/S3）、最后才谈数量（S4）。数量门槛不允许用分开的统计拼出来。
