# VULNMAP 平台当前方案汇报稿

版本：2026 年 11 月 16 日｜建议时长：12—15 分钟  
配图顺序：01 平台架构图 → 02 技术路线图 → 03 挖掘流程图。

## 开场：平台现在解决什么问题

各位老师好，下面汇报 VULNMAP 漏洞发现平台目前的架构、技术路线与实现进展。

这次方案相对之前有一个核心调整：平台的发现主线不再围绕已知案例的复现，也不再以 CyberGym、ExploitGym 的任务分流作为总体架构，而是从目标源码和构建方式出发，尝试形成“源码分析、假设生成、种子构造、覆盖率 Fuzz、验证复核和报告归档”的发现流程。原有复现与展示代码仍有保留，但不能把它们等同于新的 Discovery 主线已经完整接入前端。

我们对模型和工具的职责作了明确划分：模型负责提出值得验证的假设，Fuzz 和实际重放负责提供执行证据，复核门禁负责限制最终结论。平台不会因为模型判断有漏洞，就直接将它登记为确认漏洞。

## 第一张图：平台总体架构

请看第一张平台架构图。平台当前采用集中式 Campaign 编排，而不是多个智能体自由协商的分布式系统。发现入口主要是命令行，输入包括源码或二进制，以及 target.yaml 等构建描述。

整体分为五层。最上面是入口与配置层，负责目标接入、构建方式和模型环境配置。这里同时标出了历史 Web 展示，目的是区分已有展示能力与新发现引擎，避免把旧页面的存在当作新功能已经全部接通。

第二层是集中式编排层。Campaign 按 D0 到 D5 的顺序组织任务，处理选点、执行时长、并发和失败记录。调用点可以按固定评分排序，也可以采用随机顺序，供后续对照实验使用。

第三层是 Agent 与分析层，也是模型发挥作用最直接的位置。静态模块先生成目标画像和危险调用点，再将选中的调用点及源码窗口交给分析 Worker。分析默认尝试 LLM，输出假设、置信度和源码引用；无 Key 或模型调用失败时，转入规则分析，并记录实际使用的模式。因此，“配置默认是 LLM”和“某一次任务确实调用了 LLM”是两个不同事实。

分析结果进一步交给规则种子构造器。这一步不是让模型任意生成可执行程序，而是根据假设中的长度、数量、偏移、格式字段等线索，在已有 JSON、PNG、TIFF 等模板中选择和补充测试输入。

第四层是 Fuzz 与验证层，包括目标 harness、覆盖率引导变异、ASAN 诊断、干净重建与重放。harness 是把文件输入接到目标程序或库 API 的最小测试入口；不同 API 路径需要不同 harness，不能认为有一个入口就覆盖了整个库。

执行隔离方面，auto 模式优先选择 bwrap，其次是 unshare；如果隔离不可用且未要求强制隔离，存在宿主执行回退。因此正式运行需要使用 require-isolation 选项，要求隔离不可用就失败，不能笼统宣称所有运行都必然处于沙箱。

最后一层是数据、报告与评估层。节点主要通过内存中的字典和列表传递结构化结果，同时将结果保存为 JSON。原始种子、崩溃输入、构建产物和日志作为独立文件保存，报告与 SQLite 台账用于归档和审计。这不是每个节点都重新读取 JSON 的文件驱动工作流，目前也不能据此宣称支持任意节点断点恢复。

## 第二张图：核心技术路线

第二张图说明整个方法如何从源码走到可审计的结果。

第一步是目标画像和调用点建账。平台扫描入口、函数、危险调用与参数线索，通过近似可达性和固定评分选择分析位置。这里的调用图和评分是轻量近似，不是完整的程序语义证明。

第二步是 Agent 分析。LLM 接收调用点元数据与局部源码，提出可验证的漏洞假设，并给出引用。它不能执行目标，也不直接给出漏洞确认结论。引用和输出格式需要校验，但引用存在并不意味着模型的推理必然正确。

第三步是把假设转为测试方向。例如，模型认为长度计算可能有问题，构造器就追加边界长度或超长输入；认为 PNG 宽高处理有风险，就选择相关字段的边界样本。随后，自建 Fuzz 引擎对这些输入进行变异与执行，利用覆盖位图、比较反馈和字典信息扩展探索。这里既有源码语义提供的先验，也有执行覆盖提供的反馈，两者共同影响测试，但不是一个已经具备自主反思能力的模型闭环。

第四步是分诊与复核。Fuzz 发现的崩溃首先只是候选，需要解析诊断、按栈签名去重，并在独立干净构建上用同一个输入重放三次。复核默认采用规则，也可以显式开启单次 LLM 复核，但模型不能突破证据门禁，也不能把结论提升到规则证据不支持的等级。

第五步是报告与效果评估。报告记录完整性、覆盖情况、发现条目与缺失证据。同时，通过 ranked 与 random，以及假设驱动种子与基础种子的对照，评估各部分是否有效。要单独证明 LLM 的贡献，还需要严格区分 LLM 假设、规则回退假设和基础种子，并控制目标、初始语料、执行预算和重复次数，不能仅凭功能接通就宣称模型带来提升。

## 第三张图：实际挖掘流程与节点工具

第三张图把方法展开到实际模块。

D0 由 profile.py 建立静态档案，形成 target.json；D1 由 callsites.py 建立并排序调用点台账，形成 callsites.json。D1.5 由 agents.py 组织线程池，为不同调用点并行执行分析任务，形成 hypotheses.json。

Agent 的主要价值就在这里：将“发现了某个危险函数”进一步转为“这个调用位置可能存在什么问题、应优先测试什么条件”。不过，当前属于任务级并行分析，不等于多个长期运行、能自主调用工具并互相协作的智能体。

随后进入 D2。targetspec.py 读取构建描述，接入 main、内置 API 或自定义 harness；propose_seeds 根据假设线索构造种子；covfuzz.py 负责并行覆盖率 Fuzz。运行时覆盖信息再映射到源码位置与函数，回写调用点台账。报告需要区分行级命中和函数级命中，不能把函数被执行说成具体危险调用行已经被命中。

D3 使用 triage.py 解析并复现崩溃，D3.5 进行复核。最终结论分为 confirmed、weakened、excluded 和 needs_human。在当前规则口径下，有效写入型诊断、干净构建和三次稳定复现支持 confirmed；稳定的读越界或 UB 通常记为 weakened；无法复现或证据不足则排除或留待人工处理。这些都是平台内部的证据分级，不能直接等同于高危、可利用或新 CVE。

D4 汇总 JSON、Markdown 和 SQLite 台账；D5 执行策略与种子对照。失败、超时、未覆盖和零崩溃都应作为结果保存，而不是只展示成功案例。

## 当前实现与已有结果

接下来介绍当前进展。以下数字来自已归档的 campaign 与实验记录，不是本次更新图片时重新执行的结果；不同目录对应不同构建、harness 和预算，不能混合当作同一轮实验。

受控样例方面，基础解析器、PNG 和 TIFF fixture 的归档结果各有一个 confirmed 写入型问题。它们用于验证发现、重放与归档链路，不能冒充真实软件中的未知漏洞发现。

真实目标方面，cJSON 的 Minify 路径归档了一处读越界，在干净构建上三次复现，结论是 weakened；其调用点覆盖记录为 14/80，且这 14 个命中是函数级口径，不代表全部调用点都被逐行覆盖。

另一个例子是 libtiff 的 Strip 路径。归档记录显示 TIFFRawStripSize64 出现读越界，干净构建三次复现，仍归为 weakened。这个结论依赖当前 harness 的 API 调用方式；其实际 API 使用前提和安全影响仍需进一步核查，不能直接升级为新漏洞或高危声明。

负结果也需要同时说明：libpng 的逐行读取路径归档了 70,147 次执行、零崩溃；cJSON 的 Parse/Print 路径归档了 76,939 次执行、零崩溃。零崩溃并不等于目标安全，只说明对应入口、语料和预算内未观察到崩溃。

LLM 方面，已有两个 live 归档任务记录实际进入 LLM 分析，而不是规则回退。但 cJSON 的模型假设与最终 Minify 崩溃点并不一致，这说明模型可以提供线索，也可能判断错误，实际执行和复核仍不可替代。已有种子 A/B 记录不足以证明 LLM 带来显著提升，我们暂不作效果领先的结论。

## 不足、下一步与结束

目前平台的主要不足有三点：第一，分析主要依赖局部源码窗口与近似调用关系，跨函数数据流理解仍有限；第二，模型主要通过规则种子模板间接影响测试，尚不是自主规划、调用工具、反馈修正的完整 Agent；第三，真实目标覆盖与 harness 深度仍有限，新的 Discovery 报告展示也需要继续接入前端。

下一步首先扩展 harness 与源码上下文，优先改善真实目标中未覆盖的路径；其次开展固定预算、多次重复的 LLM、规则假设与基础种子消融实验，将模型成本、覆盖增量、首次崩溃时间和可复现缺陷数量一起报告。

总结来说，当前平台已经形成“分析提出假设、假设指导规则种子、Fuzz 产生候选、干净重放与门禁约束结论”的实现链路。我们希望提高测试的针对性，但不会将模型输出当作漏洞事实，也不会将一次崩溃当作高危成果。我的汇报到这里，谢谢各位老师。
